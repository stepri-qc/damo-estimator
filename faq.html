General

What the tool is and isn't.

QWhat is this tool, in one sentence?
A

An interactive RFP-sizing tool for DAMO managed services that turns a written estimation framework into a working calculator, producing a year-on-year effort and FTE estimate, a named role-and-grade staffing plan, and an explicit confidence posture.

QWhat does it NOT do?
A

It sizes effort and headcount only. There is no rate card, no margin and no client price anywhere in the tool — pricing stays in the existing commercial workbook. That was a deliberate scope decision, not an oversight.

QWhat is it built from?
A

Two source documents: the DAMO Solution Estimation Framework (a 30-page PDF) and the AI/Works DAMO Team Pricing Sheet (a 7-sheet workbook). Every mechanic traces to one of the two, tagged [F] or [P] in the code and the interface. Anything not traceable to either is explicitly flagged proposed and listed in the exported register — a calibration target, not a fact.

QWho is it for?
A

Solution architects sizing an AMS/IMS/DMS proposal, and anyone who needs to defend an estimate's arithmetic in front of a client or a deal review.

Using it

Getting from a blank estimate to a defensible number.

QHow do I get started?
A

Two ways in. On a fresh visit the tool opens on an intake screen — add the RFP or any supporting document and let it pre-fill what it can, or click “Skip — set up manually.” Either way you land on a dashboard that already loads with a single AMS tower and a worked default, so there are live numbers on screen immediately. From there: pick the service mix, set who provides each support tier, score the confidence and risk drivers, and read the results.

QCan I upload the RFP as a file instead of typing everything in?
A

Yes — .docx, .pdf, .xlsx, .txt and .md are all supported as direct file uploads, no conversion step. Word and Excel are parsed natively in the browser; PDF uses a real bundled parser (pdf.js), since PDF's internal structure genuinely needs one. You can also add more than one document — the RFP itself, a separate incident-history workbook, an SLA sheet — and they combine into a single pass rather than needing to be merged by hand first. The intake screen is reachable any time via Start from RFP in the masthead, not just on first load.

QDoes the intake screen give me an AI-written summary of the RFP?
A

Not automatically on every deployment — and it says so on screen rather than pretending otherwise. What always runs automatically is a pattern-matcher: known DAMO phrasing (contract term, service towers, incident volume, SLAs, coverage, AIOps intent) gets pre-filled, with the exact source excerpt shown behind every match. That's regex, not comprehension. See the next question for the two ways to get a genuine, model-written summary.

QSo how do I get an actual AI-generated summary?
A

Depends which deployment you're on:

  • On the Netlify site (damo-estimator.netlify.app): click Extract with AI now in the intake screen's “Import Claude-prepared inputs” panel. It sends your document text to a real backend function that calls Claude directly and writes the structured JSON straight into the box below — no copy-paste, no second window. Usually done in 10–15 seconds, with a live status line showing progress and token usage.
  • Everywhere else (including the private Artifact, which has no way to call an external server): use Copy prompt for Claude in the same panel. One click copies instructions, the target schema, and the document text you've entered into your clipboard. Paste that into a fresh Claude conversation, and paste the JSON that comes back into the “Prepared JSON” box.

Either way, hit Apply prepared inputs. The real summary lands as a Document Summary card at the top of the dashboard, and flows into the exported register and the printed report.

QHow do I print or save the estimate as a PDF?
A

Print / Save PDF in the masthead shows an SA-only report on screen — effort, FTE, roles, confidence, the assumptions register, deliberately excluding the optimization/QUBO material a client proposal doesn't need. From there, press Ctrl/Cmd+P and choose “Save as PDF” as the destination. The button shows the report rather than triggering the print dialog itself, because a published Artifact's sandbox can silently block a scripted print call; your browser's own print shortcut is never subject to that restriction.

QWhat if the client can't give me historical ticket data?
A

Two fallback demand bases: a complexity-point proxy (apps sized S through XXL, each with a benchmark tickets-per-month range) or a MAU-based estimate (monthly active users × an industry incident-rate benchmark). The tool auto-selects the right one of four estimation scenarios based on data availability and client AI maturity, and adjusts contingency and confidence accordingly.

QHow does “service responsibility” work?
A

Each tower declares who provides L1, L2 and L3 — DAMO, the customer, another vendor, or the client's own product team. Tiers not provided by DAMO are not sized at all: no effort, no headcount, no roles — though ticket volume still cascades through them, because an upstream party's resolution rate still sets the volume DAMO has to handle downstream.

QHow do roles get selected?
A

Only nine of the client's 37 named roles are switched on by default — the ones actually used in practice, not a weighted contest across the full list. Role choice is threshold- and flag-driven where the real staffing heuristic is: a Systems Support Engineer covers AMS L3 below an evolution-effort threshold, a dedicated Developer only above it; SRE is included in the IMS mix only when the client has explicitly named reliability as an objective. Every other role stays available — switched off, not deleted — for the deal that genuinely needs it.

QWhat's Engagement type (Greenfield / Brownfield), and does it actually move the number?
A

It says who built and knows the system — a different axis from Estate profile, which is about how modern the tech stack is, not who built it. Greenfield (built and run by Thoughtworks from the start) is high confidence. Brownfield (an existing build being handed over) is the conservative default, and yes, it genuinely moves the number two ways: it auto-seeds four Annexure 1/2 confidence and risk sliders lower, and it applies a direct Year-1 FTE uplift (default +20%) on top of that, tapering to zero by Year 3 as the team gets a full year to learn a system it didn't build. Switching the toggle always re-seeds the four sliders, even over a manual edit; all four stay freely editable afterward.

QWhat's the delivery-location mix for?
A

Team-loading across four regions: IME, EU, APAC and NA. IME shows the whole team as delivered from India, no configuration needed. EU unlocks an onshore (Europe) / nearshore (Romania) / offshore (India) split; APAC splits across China and Australia; NA splits across nearshore (LATAM/Ecuador) and offshore (India) — each with its own quick presets. Every region remembers its own mix independently, so switching to compare two regions never loses what you entered in the other. It's applied uniformly across the already-computed role and grade allocation — a staffing-location layer, not a change to total headcount.

QI entered environment/hosting/database counts on an IMS tower (or data-product/integration counts on DMS) and the FTE and role mix changed. Why?
A

That's a second complexity axis, separate from demand basis. Demand basis (history/complexity-proxy/MAU) says how many tickets a tower will generate; these new IMS/DMS-only fields say how operationally complex the estate itself is to run — more environments, hosting targets, databases, integrations and dependencies mean more non-ticketing overhead regardless of ticket volume. They compute a score that does two things: continuously bumps the tower's B-factor (10% at the Low/Medium cut-point, 20% at Medium/High, still climbing past that, capped only against extreme adversarial input) — so bigger inputs keep moving the FTE rather than plateauing once you cross into High — and, via the same score's Low/Medium/High badge on the tower card, makes Information Security Engineer (IMS) or Data Architect/Data Strategist (DMS) eligible only at High, provided you've also switched that role on in Roles & grades. AMS is untouched; its existing incident-history inputs already cover it. Every weight and cut-point behind the tiering is editable in the Benchmarks panel and flagged proposed — it's grounded in a supplied Data Managed Services deck's complexity framing, not the original [F]/[P] sources.

QWhat's the difference between Active-Active and Active-Passive off-hours coverage, and does it actually change the number?
A

It's a per-tower choice, shown whenever the coverage window is anything other than 8x5 (8x5 has no off-hours to speak of). Active-Active means every declared hour is fully, actively staffed — dedicated people, off-hours included, same as business hours. It's the default, and it reproduces the tool's original shift-floor formula exactly, so no existing saved estimate silently loses headcount. Active-Passive means the team is actively staffed during business hours and on call for P1-critical incidents only outside them — P2–P4 off-hours requests queue until business hours resume. Yes, it genuinely moves the number: business hours stay fully staffed, but the off-hours portion of the window is discounted to an on-call allowance (default 15% of a dedicated shift, editable), which can cut the coverage floor dramatically on a low-demand 24x7 deal — we verified roughly a two-thirds reduction on a real test case. For Active-Passive, the tool also auto-suggests which delivery location typically carries the on-call — usually Offshore/India, per your Customer Region and delivery-location mix — as a proposed, editable convention, not a computed cost fact (the tool has no rate data to derive "cheapest location" from).

Trusting the numbers

Why the output isn't a black box.

QHow do I know the numbers are actually right?
A

The built-in “Verify against framework” panel runs 107 checks on every render, most of them worked examples lifted directly from the source documents — the framework's own page-3 illustration, its Annexure 1 and 2 examples, the shift-coverage maths — plus synthetic cases for logic that has no source-document analogue, like the intake extraction engine, the document-summary hand-off, the AI-extracted-tower completeness check described below, and the IMS/DMS structural-complexity model (including a direct regression test for a real reported defect, where the complexity bump used to stop moving the FTE once a tower crossed into “high,” no matter how much further the inputs went). A green run means the engine reproduces the document it claims to implement. It's designed to be run live in front of a client as a credibility check, not just a developer test suite.

QDid building this find any errors in the framework itself?
A

Yes — one. The framework's Annexure 2 worked example lists nine weighted risk-drag values that sum to 14.25, but the framework's own total row prints 15.3. The band conclusion (Medium) holds either way, but the tool sums the rows correctly and flags the discrepancy rather than silently matching the typo.

QWhat exactly does the confidence score change?
A

Two things: the contingency and commercial-posture recommendation shown in the results, and — more substantively — the width of the Monte Carlo uncertainty bands on the FTE trajectory. A weaker evidence base doesn't just get a lower label, it visibly widens the P80 estimate.

QWhat's still “proposed” rather than framework-sourced?
A

The P1–P4 severity-to-tier routing matrix, per-tower ARE multipliers and automation ceilings, the AIOps use-case catalogue's effort and deflection numbers, the role-policy thresholds, the Greenfield/Brownfield slider seeds and FTE-uplift figure, the APAC/NA location presets, and the IMS/DMS structural-complexity weights, cut-points and B-factor bumps. All are editable, all are flagged, and all are listed together in a calibration backlog inside the register export — the honest list of what needs real engagement data before it should be trusted at face value.

QI applied AI-extracted or hand-pasted JSON and the team size looked much too small. What happened?
A

This was a real bug, now fixed: a partial tower object from an AI extraction (correctly omitting fields it had no evidence for) or a hand-written partial JSON could land in the estimator missing a field like enabled — and every calculation silently skips a tower that isn't marked enabled, with no error shown. The fix backfills every applied tower against the same complete-tower template a manually-added tower gets, keeping anything the source JSON actually provided and filling in the rest. If you're still seeing this on an old saved link, the fix hasn't reached that bookmarked hash yet — see the next section.

The quantum & optimization layer

Where the quantum-computing study actually connects.

QWhere does quantum computing actually show up?
A

Four genuinely combinatorial sub-problems inside the estimation process — which AIOps use cases to fund and when, follow-the-sun shift rostering, team-shape optimization, and uncertainty propagation — are formulated as QUBOs (Quadratic Unconstrained Binary Optimization problems), the native input format for quantum annealers and QAOA circuits.

QIf it's about quantum computing, why does it use classical solvers?
A

Because at DAMO's actual instance sizes — a handful of AIOps use cases, a few dozen weekly shifts, well under thirty people — classical exact methods (branch-and-bound, integer programming) solve these in milliseconds, and there is nothing for a quantum device to win. The QUBO formulation is included as a rigorous problem statement and an annealer-ready export, not a performance claim. The tool says this plainly rather than implying an advantage that isn't real at this scale.

QWhich of the studied algorithms actually apply?
A

Three of seven, honestly assessed:

  • QAOA and quantum annealing — best fit, attach directly to the three QUBO problems with no reformulation needed.
  • Quantum Amplitude Estimation — best theoretical fit for the uncertainty-propagation problem; the estimate genuinely is E[f(X)], and QAE's O(1/ε) sample complexity beats classical Monte Carlo's O(1/ε²) in principle.
  • VQE — works but degenerates into QAOA, since the Hamiltonian here is diagonal.
  • Grover — technically applicable, practically irrelevant: quadratic speedup on a search space of a few hundred configurations a classical machine enumerates instantly.
  • HHL and quantum walks — no natural fit. No sparse linear system of meaningful size, no graph-traversal problem of meaningful size.
QWhat's a QUBO, in plain terms?
A

A way of stating an optimization problem as: choose a set of yes/no decisions (binary variables) to minimize a score, where the score is built from single-decision terms and pairwise-interaction terms between decisions. Constraints get encoded as penalty terms large enough that violating them can never look cheaper than obeying them. It's the standard input format quantum annealers and QAOA circuits actually accept.

QCan I export the QUBO and run it on real quantum hardware?
A

Yes — the QUBO inspector panel exports the Q matrix as JSON, ready to hand to an annealer or a QAOA toolchain. The panel also shows variable count, matrix sparsity, and the penalty-weight reasoning, so the encoding is auditable rather than a black box.

Limitations & roadmap

What's next, and what this deliberately doesn't do.

QCan this tool price a deal?
A

No, by design. It stops at effort and headcount. Turning that into a price is a separate step in the existing commercial workbook, deliberately kept out of scope so the estimate stays defensible independent of margin decisions.

QWhy can't a published tool like this just call an AI model directly?
A

The private Artifact genuinely can't — checked, not assumed, against the platform's own capability list, which covers only file downloads and calling the viewer's connected tools, nothing that can generate or summarize text. That's still true for the Artifact and is exactly why it offers the copy-to-Claude hand-off instead. The Netlify deployment is a real web server, though, so it's a different case: it runs an actual serverless function that calls Claude with a server-held API key, which is what powers the one-click Extract with AI now button there (see “So how do I get an actual AI-generated summary?” above). The two deployments genuinely differ on this point — it isn't a limitation of the page itself, only of a page with no backend behind it.

QWho pays for the AI extraction calls on the Netlify site, and is my document text safe?
A

The site owner's own Anthropic API key, held as a server-side environment variable the browser never sees and this repository never contains. An optional shared passphrase can gate the extraction endpoint so a stranger who finds the URL can't spend the owner's credits — that's an abuse guard, not a login system. Your document text is sent to Anthropic's API to generate the extraction and is not stored anywhere by the tool itself; nothing is written to a database, since the whole tool still has none — every estimate lives only in your own browser's URL.

QI reloaded a bookmarked estimate and a feature I know shipped doesn't seem to be there. What's going on?
A

Almost always a stale saved link, not a bug. Every estimate lives entirely in the URL's #hash, captured at whatever version of the tool you were using when you last edited it — so an old bookmark can carry a state object from before a newer field existed. A same-URL hard reload doesn't clear this, because the hash travels with the URL. Opening the bare URL with no #fragment, or clicking Reset, will.

QDoes the document intake handle scanned or image-only PDFs?
A

No — it reads the text layer a normal PDF export already has, not pixels. A scanned document with no embedded text layer won't yield anything, because that would need OCR, which is out of scope. If a PDF isn't extracting cleanly, paste the text in directly instead.

QWhat would it take to run this on real quantum hardware?
A

Problem sizes that don't exist yet at DAMO's scale. The honest answer, and the one in the tool, is that classical solvers win outright today — the value of the QUBO layer right now is the rigor of the formulation and the optionality it creates, not a live performance advantage.

QWhat's the single highest-value thing to calibrate next?
A

The AIOps use-case catalogue's effort and deflection estimates — they drive both the portfolio-optimization funding decisions and the whole year-on-year productivity narrative, and right now they're the tool's own best guess rather than data from real engagements.
